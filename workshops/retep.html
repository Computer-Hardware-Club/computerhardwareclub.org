RETEP: The Peter Incident

A suspicious installer has turned up on Peter. Run it in your team’s Linux VM, follow the evidence, and get Peter back to normal.

AI assistance is off for this workshop. Club officers can help with terminal syntax.

Start the incident

Sign in with your team credentials. Run the installer as your team user inside the workshop VM.

cd ~/Downloads && ./GTA-VI-Installer.run
Open workshop terminal
  1. Logs & configuration
  2. File access
  3. Processes & services
Terminal basics

The terminal has a current folder, just like a file browser. Replace uppercase placeholders in the guide with the names or values you find in the VM.

pwd
Print the current directory.
ls -la
List files, including hidden ones, with details.
cd DIR
Change directories. Use cd ~ to go home.
less FILE
Read a file one screen at a time. Press q to quit.
grep -n 'PATTERN' FILE
Show matching lines and their line numbers.
sudo COMMAND
Run a command with administrator privileges.

Start with the logs

Find the service that failed and read the journal entries from its latest startup. The journal is the service’s activity history. Use the first error from that attempt to decide what to inspect.

Check Peter’s backups

Look for Peter’s maintenance notes and backups in your home directory (~). Find a verified snapshot for the installed version, then compare its config with the live one. Use the diff and the journal error together to decide what to change.

Restart the service after editing and read the newest log entries. If the error changes, follow the new message.

Logs & configuration commands

systemctl --failed
List failed units.
systemctl status SERVICE
Show the service’s state and recent log messages.
sudo journalctl -u SERVICE -n 20 --no-pager
Read the last 20 journal entries for the service.
diff -u LIVE_CONFIG BACKUP_CONFIG
Compare the settings in two files.
sudo nano FILE
Edit a protected file. Press Ctrl+O, then Enter to save. Press Ctrl+X to exit.
sudo systemctl restart SERVICE
Restart the service so it reads the updated config.

Check file access

If the journal says the service can’t open a file, inspect the path in the error. Compare its owner, group, and permissions with the corresponding file in the verified backup or with the metadata recorded alongside it.

Check who needs access

File permissions work like keycard access. Each file has separate rules for its owner, its group, and everyone else. Check the service definition for the account it runs under, then work out which rules apply to it.

After repairing access, restart the service and look for a successful startup in the journal.

File access commands

stat FILE
Show the owner, group, and permissions, including the numeric mode.
ls -l FILE
Show ownership and permissions in a single line.
systemctl cat SERVICE
Show the service definition and any overrides. Look for User= and Group=.
id USER
Show the account’s user ID and group memberships.
sudo chown OWNER:GROUP FILE
Set the file’s owner and group.
sudo chmod MODE FILE
Set the file’s access permissions.

Investigate the slowdown

With Peter’s service back, look at what’s using CPU and memory. Compare the process names and command lines with the installed services to see what’s managing the activity.

Check what can start it again

A process is a running program. Systemd acts like a supervisor for services and can start them at boot or restart them when they exit. Once you’ve tied the unexpected process to a service, check both whether it’s running now and whether it’s enabled.

After making a change, check resource usage again and confirm the service’s startup setting.

Process and service commands

top
Watch CPU and memory use by process. Press q to quit.
free -h
Show memory usage and how much is available.
ps aux
Take a snapshot of running processes and their command lines.
systemctl list-units --type=service
List active and failed service units.
systemctl list-unit-files --type=service
List installed service definitions and their startup settings.
systemctl is-enabled SERVICE
Check whether a service is enabled to start automatically.
sudo systemctl stop SERVICE
Stop a running service.
sudo systemctl disable SERVICE
Remove the links that enable a service to start automatically.

Verify recovery

Run the check in your workshop terminal. When it prints RESULT: COMPLETE, show a club officer what tipped you off, what you changed, and how you verified the fixes.

check-system
